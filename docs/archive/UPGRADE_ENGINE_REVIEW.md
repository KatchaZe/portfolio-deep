# ประเมิน UPGRADE_ENGINE.md — ทำเองตามคู่มือได้จริงไหม?

เขียนหลังจาก **ลงมืออัปเกรด v7.3 → v8.2 จริงทุกขั้นตอน** (ไม่ใช่อ่านเฉยๆ) จึงเทียบได้ว่า
คู่มือบอกครบ/ถูกตรงไหน และตรงไหนที่มือใหม่จะ "ติด" เพราะคู่มือไม่ได้พูดถึง

---

## สรุปคำตอบสั้น

| สถานการณ์ | ทำเองตามคู่มือได้ไหม |
|---|---|
| **อัปเกรดเล็ก** (เปลี่ยนค่าคงที่ / น้ำหนัก / สูตรเดียวที่ signature เท่าเดิม) เช่น ERP 4.75→5.0 | ✅ **ได้** — กลไกในคู่มือถูกต้อง ผมยืนยันแล้วว่าใช้ได้จริง |
| **อัปเกรดใหญ่** แบบ v8.2 (เปลี่ยน signature + ต้องเติม data ใหม่ + ตัดสินใจว่าอะไรพอร์ตได้) | ⚠️ **ไม่ได้ทั้งหมดถ้าใช้คู่มือนี้เดี่ยวๆ** — จะติดอย่างน้อย 4 กำแพงที่คู่มือไม่ครอบคลุม |

คู่มือนี้เขียนมาดี **สำหรับเคสเล็ก** (เดโม่ของมันเองคือเปลี่ยน ERP ค่าเดียว) แต่ v8.2
เป็นการกระโดดใหญ่ที่เกินกว่าที่คู่มือเตรียมไว้

---

## ส่วนที่คู่มือ "ถูกและครบ" (ตรงกับที่เจอจริง)

1. **สถาปัตยกรรม contract เป็นเรื่องจริง ใช้ได้** — ผมแก้แค่ engine + register + สลับ config
   แล้ว store/API/หน้าจอ **ไม่ต้องแตะเลย** จริงตามที่คู่มือสัญญา (กฎเหล็กบรรทัด 20)
2. **สเต็ป 1–2** (ก็อปไฟล์ / เปลี่ยนชื่อ class + version) — ถูกเป๊ะ
3. **สเต็ป 4–5** (register ใน `__init__.py` + `DEEP_VERSION`) — แค่ 2 บรรทัด + 1 บรรทัด ตามที่บอกจริง
4. **สเต็ป 6–7** (เพิ่มเทสต์ + รัน) — แนวทางถูก และ test_engine แบบ contract **จับบั๊กได้จริง**
   (จับว่าผมยังไม่ได้อัปเวอร์ชัน)
5. **Rollback** (บรรทัด 159) — แม่นยำ: เก็บ v7.3 ไว้ สลับ config กลับได้ใน 5 วิ
6. **กรณีพิเศษ: ต้องใช้ข้อมูลใหม่** (บรรทัด 174–186) — **ลำดับถูกต้อง**: facts → source →
   normalize → validate → engine. v8.2 ใช้ลำดับนี้เป๊ะ
7. **ส่วนเทียบ 7.3 vs ใหม่** (บรรทัด 163–170) — ผมใช้สูตรนี้จริงเพื่อเทียบผล

## ส่วนที่คู่มือ "ขาด" — จุดที่มือใหม่จะติด

### 1. ไม่เตือนเรื่อง "signature ripple" (สำคัญสุด)
สเต็ป 3 บอก "แก้ math ในฟังก์ชัน เช่น `wacc()`" — เหมือนแก้ในที่เดียวจบ
แต่ v8 เปลี่ยน **หน้าตา (signature)** ของ `wacc()`:
`wacc(rf, beta)` → ต้องการ `(rf, beta, equity, debt, cash, tax, interest, opinc)`
การเปลี่ยน signature **กระเทือนทุกที่ที่เรียกใช้** + เปลี่ยน signature ของ `reverse_dcf()` ด้วย
ถ้ามือใหม่แก้ `wacc()` ทับของเดิม โค้ดส่วนอื่นจะพังทันที
> คู่มือควรเตือน: "ถ้าสูตรใหม่ต้องการ input เพิ่ม = signature เปลี่ยน → ต้องแก้ทุกจุดที่เรียก
> (หรือเขียน engine ไฟล์ใหม่ทั้งไฟล์ ซึ่งปลอดภัยกว่า)"

### 2. ไม่พูดถึงช่องว่าง "skill ≠ dashboard"
สกิลเป็น workflow โต้ตอบที่ใช้ **Bigdata + วิจารณญาณคน**; dashboard เป็น **ระบบอัตโนมัติ free data**
คู่มือสมมติว่า "math ในสกิล = math ใน engine 1:1" แต่จริงๆ ราวครึ่งหนึ่งของ v8.2
(Bigdata pull, Monte Carlo, peer median, การให้คะแนนด้วยคน) **พอร์ตตรงๆ ไม่ได้**
คู่มือ **ไม่มีวิธีคัดว่า "อันไหนพอร์ตได้/ไม่ได้"** → มือใหม่จะพยายามทำ peer-median/Monte-Carlo แล้วตัน
> นี่คือกำแพงที่ใหญ่ที่สุด

### 3. ไม่สอน "ทำยังไงเมื่อไม่มี free source" (graceful degradation)
กรณีพิเศษบอกแค่ "เติม facts + source" แต่ไม่บอกว่าจะทำยังไง **ถ้าไม่มีแหล่งฟรีให้ดึงเลย**
ของจริงต้องใช้แพตเทิร์น **skip + flag** (ไม่มั่วค่า) ตาม invariant 17 ของ v8.2 เอง —
มือใหม่จะไม่รู้ว่าควร degrade อย่างสุภาพแทนที่จะ hard-fail หรือเดาตัวเลข

### 4. ประเมินขนาดงาน "เติม data" ต่ำเกินจริง
กรณีพิเศษถูกเขียนเป็นเชิงอรรถสั้นๆ 5 บรรทัด แต่กับ v8.2 มันคือ **งานก้อนใหญ่ที่สุด**:
เพิ่ม 6 field ใน SEC extractor + เขียน accessor ใหม่ (`instant_series` สำหรับค่าย้อนปี) + FX +
normalize. และคู่มือ **ไม่มีตัวอย่าง** การต่อ SEC extractor ซึ่งมี gotcha จริง —
เช่น `ttm()` รับ concept **ตัวเดียว** ต้องร้อยด้วย `or` (ผมเจอบั๊กนี้ตอนทำจริง)

### 5. ไม่เตือนเรื่อง "ผลลัพธ์เพี้ยน" ต้องมี sanity guard
สูตร v8 fundamental PEG ที่ "ถูกต้องกว่า" กลับให้ค่า **ABBV = $1,131** (เพราะ low-beta →
discount ต่ำ → terminal multiple ระเบิด) ต้องใส่ guard (Ke floor + clamp PE) ถึงจะสมเหตุผล
คู่มือไม่เตือนว่าสูตรใหม่อาจพ่นค่าเพี้ยน และไม่บอกวิธีเช็ก (เทียบ v7.3 + ส่องหุ้นที่คุ้น)

### 6. "เพิ่มเทสต์" ไม่พอ — เทสต์เดิมที่ pin เวอร์ชันเก่าจะพัง
สเต็ป 6 บอกแค่ "ก็อปบล็อกเทสต์ เปลี่ยนเวอร์ชัน" แต่จริงๆ ผมต้อง **แก้เทสต์เดิม**
(`test_engine` ที่ assert `v.version == "7.3"`) เพราะพอสลับ engine มันจะ fail
คู่มือควรบอก: "หาเทสต์ที่ผูกกับเวอร์ชันเดิมแล้วอัปเดตด้วย"

### 7. ไม่พูดถึง changelog หลายชั้น / การพอร์ตบางส่วน
v8.0/8.1/8.2 ซ้อนกัน 3 ชั้น คู่มือสมมติว่ามี "เวอร์ชันใหม่" ก้อนเดียวสะอาดๆ
ของจริงต้องอ่าน 3 changelog แล้วตัดสินใจพอร์ตทีละชิ้น — ไม่มีคำแนะนำตรงนี้

## ข้อเสนอแก้คู่มือ (เพื่อให้ทำ v8.2-scale เองได้จริง)

1. เพิ่มสเต็ป 0.5 **"คัดว่าอะไรพอร์ตได้"**: จัดแต่ละการเปลี่ยนแปลงเป็น 5 กลุ่ม —
   (a) ค่าคงที่ (b) สูตร signature เท่าเดิม (c) สูตร signature เปลี่ยน → เขียนไฟล์ใหม่
   (d) ต้องใช้ data ใหม่ → เช็ก free source (e) ไม่มี free source → skip+flag
2. ใส่กล่องเตือน **"signature ripple"** (ตามข้อ 1 ข้างบน)
3. ขยายส่วน "เติม data" ให้มี **ตัวอย่างจริง** การต่อ SEC extractor + gotcha (`ttm()` ตัวเดียว, instant vs flow)
4. เพิ่มสเต็ป **"ส่องผลลัพธ์"**: รันตารางเทียบ v เก่า/ใหม่ + ส่องหุ้นคุ้น 3–5 ตัว ระวังค่าระเบิด → ใส่ clamp+flag
5. เพิ่มบรรทัด **"อัปเดตเทสต์เดิมที่ผูกเวอร์ชันเก่า"** ในสเต็ป 6

## บรรทัดล่างสุด

คู่มือ **เก่งเรื่องกลไก** (copy → rename → register → flip → test → rollback) และส่วนนั้น
ผมยืนยันว่า **ถูกและใช้ได้จริง** มือใหม่ทำ **เคสเล็กเองได้แน่นอน**

แต่สำหรับ v8.2 ที่ "เปลี่ยนหลายด้าน" (signature ใหม่ + data ใหม่ + ต้องคัดว่าอะไรพอร์ตได้ +
ต้องกัน output เพี้ยน) คู่มือ **ยังไม่ครบพอ** ให้มือใหม่ทำเองคนเดียวจบ — จะติดราว 4–6 จุดข้างบน
เติม 5 ข้อเสนอข้างต้นแล้วจะ "ทำเองได้จริง" ครอบคลุมถึงเคสใหญ่ด้วย
